# Codex 会话更换评估方案

方案修订：2026-11-06。接口与本机能力的核验日期为 2026-11-03；本次未重新运行能力探针。

## 结论

方案采用四个逐步增强的会话切换评估档位。S1、S2 使用程序读取和确定性规则，新增监控的模型调用为 0；S3 增加最必要的受限语义分析；S4 再扩大材料和核验范围。每个档位都输出同一种结果：切换建议分、原因、数据覆盖与未知项、档位和模型开销。默认档位为 S2，用户可在需要时选择其他档位。

S1 不是只有原始读数的采集层，而是第一版可交付的最简评分版。它在数据足够时给出粗略建议分；数据不足时给出“未评分/待评估”和缺失原因。这样 S1 可以先独立交付，S2 再在它的基础上增加更充分的确定性信号。原始读数仍保留，便于检查分数来源。

四档都面向同一个目标：提示用户是否值得考虑开新 session 继续当前任务。建议分是 0–100 的未校准排序指标，数值越高表示当前证据越支持“考虑切换”；它不是“换后成功的概率”，不表示质量下降百分比，也不保证新 session 会带来净收益。缺少关键数据时不能用 0 分掩盖未知。

S1、S2 的新增监控不向正常任务代理追加评估或自评指令，不依赖模型自报、标题含义或模型生成的健康标签。S3、S4 的模型参与是独立的可选能力，具体材料、调用路径和预算必须单独标明；“顺便分析”仍会增加模型工作或上下文成本。正常任务和既有标题功能按各自流程使用模型。

监控作为 Agent Clarity 中职责独立的可选模块；标题仍由现有标题组件负责写入。按 2026-11-03 的安装核验记录，已安装包有哈希校验，因此后续更新应走正常安装器、生成新回执并审查 Hook，不能直接改缓存。任何档位都不自动创建会话、不阻断任务、不覆盖手动标题；分数只提供建议，不替用户做切换决定。

## 本阶段的目标和边界

本阶段交付：

- 四个档位的共同输出结构、评分含义和未知状态；
- 每项数据的来源、采集验证状态、模型参与内容和额外调用预算；
- S1→S4 的逐步交付结果、日常档位行为和默认 S2；
- 零模型规则、受限语义分析、交接和效果验证的边界；
- 方案成立的事实、推理和未验证范围。

本阶段不做：

- 修改、安装或重新启用插件；
- 读取用户历史会话内容；
- 创建真实测试 session；
- 运行继续旧 session、压缩后继续、新 session 加交接的对照实验；
- 把论文、社区工具或当前经验中的阈值写成 Codex 事实；
- 把未校准的建议分写成概率，或自动根据分数切换 session。

本报告只针对 Codex，不把 Claude Code 的 Hook 事件或字段语义外推到这里。2026-11-03，本机 codex --version 的实际输出为 codex-cli 0.166.0-alpha.5.1，记录在 .local/session-renewal-research-20261103/runtime-inventory.json。以下接口事实限于当日的二进制、源码和工作区副本，不代表 2026-11-06 已重新验证当前版本。README 中的 0.163.0-alpha.10.2 是更早的验证记录。

当日核验的标题插件 hooks.json 只注册 UserPromptSubmit 和 Stop。title_guard.py 只在这两个事件上记录当前 turn_id、时间戳和标题核对状态。title_runtime.py 通过 thread/read 使用 includeTurns=false 读取标题所需元数据，没有历史回合计数器，也没有本文设计的压力监控器。

当日二进制生成的协议文件保存在 .local/session-renewal-research-20261103/schema-current。其中有：

- thread/tokenUsage/updated，字段包括 last、total 和可空的 modelContextWindow；
- turn/* 和 item/* 通知；
- contextCompaction item；
- thread/turns/list 分页接口；
- thread/read.includeTurns，但 schema 已说明完整历史水合应优先使用分页接口。

该版本的 [model_request.rs](https://github.com/openai/codex/blob/rust-v0.166.0-alpha.5.1/codex-rs/hooks/src/events/model_request.rs)导入 codex_protocol::protocol::TokenUsage，PostModelRequest.token_usage 的类型为 Option<TokenUsage>，因此可以与下文 protocol.rs 的用量字段定义对应。输入结构列出 session_id、turn_id、model、可选 agent_id/agent_type，以及 status、可空 error 字符串和 token_usage，未显式提供每次请求的独立 ID 或结构化错误码。不能用 turn_id 区分同回合的多个请求，也不能假定错误码总能直接读取；主会话/子代理归属、请求关联、排序和去重仍需探针核验。

同文件 parse_completed 将观察器 stdout 用于诊断日志，返回 data: ()；[官方 Hooks 文档](https://learn.chatgpt.com/docs/hooks)的 PreModelRequest/PostModelRequest 节也说明输出不能改变模型上下文或阻断请求。该文档另列 PreCompact/PostCompact 为压缩前后事件，但所列 turn_id、trigger 不足以唯一识别同回合多次同类压缩；失败/取消的完成判据也未由这些字段给出。身份与完成口径核验前只能记录事件，压缩总次数未知。上述源码及文档事实为高置信，目标桌面入口的实际投递仍未验证。缓存来源 URL、版本 tag 和 SHA-256 保存在研究 manifest；本次复核 model_request.rs、protocol.rs 和 hooks-current.md 的内容哈希均与原记录一致。

“无需模型即可计算”和“插件已经能可靠采集”是两件事。下表中的字段和事件都有候选来源，但新增监控器尚未做 live 验证，不能把接口存在写成运行就绪。

## 证据和适用范围

[官方 Hooks 文档](https://learn.chatgpt.com/docs/hooks)支持事件和字段的接入事实，不支持质量下降或固定阈值。[官方最佳实践](https://learn.chatgpt.com/docs/learn/best-practices)建议连贯工作留在同一 chat，在变长时使用 /compact，真正分支时再 fork。[Compaction 文档](https://developers.openai.com/api/docs/guides/compaction)说明压缩用于平衡质量、成本和延迟。这些都是高置信的产品文档陈述，未证明压缩后质量必然下降，也没有给出第 N 轮必须换的结论。

OpenAI 0.166.0-alpha.5.1 的 [release](https://github.com/openai/codex/releases/tag/rust-v0.166.0-alpha.5.1)、同版本 [token schema](https://github.com/openai/codex/blob/rust-v0.166.0-alpha.5.1/codex-rs/app-server-protocol/schema/json/v2/ThreadTokenUsageUpdatedNotification.json) 及 [protocol.rs 的 TokenUsageInfo::append_last_usage](https://github.com/openai/codex/blob/rust-v0.166.0-alpha.5.1/codex-rs/protocol/src/protocol.rs#L2541)支持以下判断：在常规追加路径，total 含已经追加的用量，last 是最近追加项，不能再重复相加。同文件的 fill_to_context_window 会填充窗口计数，令 last.total_tokens 为填充值而 input_tokens 等其他字段为默认 0；误读会把未知请求输入当成零。因此首版 I 不从 last 取值，也不能把 total 无条件当作账单消耗。这些是同版本源码事实；请求、压缩、回放的具体映射仍需桌面入口实测，不把字段名当成语义证明。

[Lost in the Middle（TACL 2024）](https://aclanthology.org/2024.tacl-1.9/)、[LLMs Get Lost in Multi-Turn Conversation（读取 arXiv v1）](https://arxiv.org/html/2505.06120v1)、[LongMemEval](https://arxiv.org/abs/2410.10813)、[RULER](https://arxiv.org/abs/2404.06654) 和 [NoLiMa（ICML 2025）](https://proceedings.mlr.press/v267/modarressi25a.html)提供了长输入、多轮交互和记忆失效的实验或评估证据。对各自测试条件中的现象有中到高置信；对当前 Codex 的阈值和换会话收益仍是未知。早期错误假设、相关内容位置和干扰信息也影响结果，因此“越长越差”不能当成普遍单调规律。

[SWE-EVO](https://arxiv.org/abs/2512.18470)、[LongCLI-Bench](https://arxiv.org/abs/2602.14337)、[Terminal-Bench](https://arxiv.org/abs/2601.11868) 和 [SWE-bench](https://openreview.net/pdf/c2a76eb44300a738cbd7cb95f5bc04df621f4d25.pdf)提供了任务结果、测试及部分进展的评估方法。[SlopCodeBench](https://arxiv.org/abs/2603.24755) 在 checkpoint 之间重置 session 数据，仍研究到代码随规格迭代演化的问题。这是“换会话未必能解决代码与设计累积问题”的反证；它不是 reset 对照实验，不能用来量化切换收益。

现成的 [agent-handoff-skills](https://github.com/orzilca/agent-handoff-skills)、[claude-context-size-guard](https://github.com/hacknitive/claude-context-size-guard)、[Codex-Monitor](https://github.com/KevinKE93/Codex-Monitor) 和 [session-handoff skill](https://github.com/forest/agent-skills/blob/main/plugins/session-handoff/skills/session-handoff/SKILL.md)可参考分级提醒、压缩边界、测量滞后、旁路和结构化 handoff。已读取前三者的实际脚本；尚未在本机运行或安装。代码能证明这些机制存在，不能证明其阈值正确。Codex-Monitor 的 JSONL/桌面注入路径与 Claude 专用 usage 算法不适合直接搬入本插件。

成本评价还参考 [Token Reduction Is Not Cost Reduction（2026 预印本）](https://arxiv.org/abs/2607.12161)：其成对 Claude Code 实验表明，减少工具文本不必然降低实际费用。采用它的“把成功结果、缓存和整项任务费用一起计算”思路；其数值不迁移到 Codex。

## 指标定义

“额外调用”指监控引起的实际模型推理请求，不是用户交互轮数，也不是工具调用数。把评估附加给主任务代理虽然可能不新增一次 API 请求，仍增加模型工作，因此前两个阶段同样禁止。一个指标若能通过预先结构化的规则检查，就不应直接归为“必须模型”。

S1 优先取得 N、I/W/P、C，并用最简规则生成建议分。S2 在 S1 的基础上接入已经能稳定取得的近期变化、明确错误和其他确定性事件，但不把开放语义判断混进来。S3、S4 可以读取后续获准的结构化摘要或选定语义材料，使用同一输出结构。任何档位都不应为了凑齐表格接入维护代价不合理的 Hook 或长连接。

### 结构检查与开放语义判断

| 指标 | 不需要模型的部分 | 自动判断时可能需要模型分析什么 | 首版 / 后续额外调用 |
| --- | --- | --- | --- |
| 约束和决定遗漏 V | 对明确结构化约束运行检查，例如允许修改的文件集合；或记录用户已确认的违约标签 | 对照有效要求和实际结果，区分遗漏、用户修改要求与有依据的新决定 | 首版不做开放语义评估，0 次；后续可选不超过已配置上限的受限合并评估 |
| 重复失败与纠错 R | 对明确任务标识、工具参数和错误签名计数；显式回滚和相同内容重读可分别记录 | 是否同一目标、是否已获得新证据、是否在重复相同错误、用户是否在纠正同一事实 | S1/S2 只保留必要事件计数，0 次；后续可选不超过已配置上限的受限合并评估 |
| 进展 M | 读取已有机器可检查的验收项、测试结果和显式里程碑状态，记录通过与撤销 | 从自然语言判断实质进展、完成程度和返工，区分无进展与必要探索 | 首版不新增进展评估，0 次；后续可选不超过已配置上限的受限合并评估 |
| 交接覆盖 H | 检查固定必需字段、引用和文件是否存在，计算结构覆盖 | 已填写内容是否准确、相关，是否遗漏接手必需信息 | 首版不把交接检查作为提醒前提，0 次；后续可选不超过已配置上限的受限合并评估 |
| 交接损失 L | 对预先列出的关键项检查显式引用、机器检查结果或人工标签 | 接手后是否误记要求、遗漏决定或无法重新定位必要事实 | 首版不采集，0 次；后续实验可用人工核验，模型仅为可选辅助 |

“可能需要模型”限定于自动处理开放语义；人工核验也是可行路径。模型输出不是判定真值，结构检查通过也不等于内容正确。不能因为没有模型就把这些未知项记为“未遗漏”“有进展”或“交接完整”。

### 四个档位与模型工作量

| 档位 | 逐步交付的新增能力 | 监控额外模型调用 | 日常使用含义 |
| --- | --- | --- | --- |
| S1 | 核心读数、最简确定性规则、共同输出结构 | 0；不附加主任务评估指令 | 最低成本的粗略评分；用于先交付和验证数据链路 |
| S2 | S1 加入更多已验证的确定性事件、近期变化和去重规则 | 0；默认档位 | 默认的零模型评分；在成本和覆盖之间取平衡 |
| S3 | S2 之外，只分析完成评分所必需的少量语义材料，例如结构化关键约束是否被遗漏 | 待单独确认的受限调用；不自动启用 | 用户选择后提高语义覆盖，目标是减少关键漏报，不承诺更准 |
| S4 | S3 之外，读取更多相关证据并做交叉核验，例如选定的任务摘要、决定和验证结果 | 更高但有上限的受限调用或材料量；不自动启用 | 用户选择后做更充分评估，目标是提高证据覆盖，不承诺收益 |

四个档位的评分方向、状态字段和原因格式相同；档位只表示使用的证据范围和资源成本，不表示分数一定更高或准确率一定更高。S1→S4 是主要开发顺序，每一档完成验收后都可以交付；同时它们保留为日常可选档位，默认 S2。当前不设计根据分数自动升级档位的机制。

S1、S2 的监控额外模型调用均为 0，附加给任务代理的评估指令也为 0。S3、S4 如采用模型，候选方式是一次有界的独立评估请求，或经明确同意后把有限材料附加到主任务请求；两种方式的成本和干扰不同，不能把 Hook 触发本身当作免费推理。相关语义项可以合并分析，自动重试也必须计入上限；失败、标签缺失或证据不足时 `score_status` 为 `insufficient_data`，不追加一轮补判，也不回落到低分。

S3/S4 的具体配置必须说明：分析目的、允许读取的材料、输入 token 上限、触发条件与频率、实际请求上限、是否影响主会话、实测耗时和费用。模型可以返回有证据的标签或疑点，程序再按共同规则生成建议分；这只是候选架构，模型标签可能漂移，也不是判定真值。开发期模型标注、自动生成交接和在线语义分析不能混入 S1/S2 的零模型范围。

### 四档共同输出

每个档位都返回同一结构，避免用户因为换了档位而改变理解方式：

| 字段 | 含义 |
| --- | --- |
| `level` | 当前档位：S1、S2、S3 或 S4 |
| `score` | 0–100 的未校准切换建议分；越高表示当前证据越支持“考虑开新 session” |
| `score_status` | `scored`、`insufficient_data` 或 `disabled`；关键数据不足时不能把分数写成 0 |
| `reasons` | 触发分数的可核对原因，标明来源和测量时点 |
| `coverage` | 已覆盖的指标、未覆盖的指标、采集时间和是否可能过时 |
| `model_usage` | 额外模型调用数、材料范围、是否进入主会话；S1/S2 固定为 0 |
| `action` | 继续观察、用户手动整理检查点、用户自行准备交接；不自动创建或切换 session |

建议分是统一的用户界面合同，不是统一的统计概率。S1 可以只用压力和边界信号，S3 可以在同一结构中增加语义证据；新增证据可能让分数上升，也可能推翻初步判断而下降。只有在预先定义“换 session 后什么算更好”、收集结果并完成校准后，才可以另行提供概率；本方案不把 68 分解释为 68% 的成功机会。

分数的初始映射、权重和候选区间必须随档位配置记录 `source`、`status`、`calibrated_on`、`model_scope` 和 `runtime_scope`。未校准时，分数只能用于排序和提醒，不能自动触发档位升级、切换或阻断。输出“未评分/待评估”是有效结果，表示证据不足，不表示低风险。

## 怎样量化

以下定义区分首版测量和后续研究指标，均不计算“模型智商分”。符号用于文档核对，不要求界面展示它们。

| 量 | 定义与更新方式 | 用途与阶段 |
| --- | --- | --- |
| 人类交互回合数 N | 按已验证的用户发起回合标识计数；工具调用、模型请求、重试和内部子代理不另加。生成期间补充消息是否构成新回合，按探针核实并公开的事件映射处理 | 首版背景量。历史未补全就显示“接管后 N 轮”；不能声称历史总数 |
| 请求输入占比 P | 最近有效请求的 I / W；保留可追溯的来源记录、模型、时间及压缩时期。来源未提供请求 ID 时须验证关联方法，不能只拿 turn_id 充当请求 ID | 首版压力信号。不能可靠对应请求时为未知；不表示质量损失比例 |
| 压缩记录 C | 记录来源和时刻；只有探针核实事件身份、成功完成判据和覆盖范围后，才对完成次数去重计数，开始不另计一次 | 首版边界信息。未通过核验则次数未知，单个 PostCompact 不能未经核实就当作一次成功完成 |
| 运行余量 B | W - I；后续观察到新输入、输出、工具结果或压缩而无新用量时标为过时，观察不完整则注明覆盖未知 | 可选派生读数，0 次模型调用；未扣除下一步输出与工具开销，不称准确剩余容量 |
| 连续性违约 V | 对当前有效约束/决定逐项列“符合、违约、未核对”，记录证据和判定者 | 后续可选质量标签；零模型版不要求代理填报 |
| 重复失败 R | 区分事件近似计数与“同目标、同错误、无新证据”的语义判断，不能将两者混称 | 前者可选辅助、0 次调用；后者留待人工或可选模型分析 |
| 进展 M | 在已有验收清单上记录新通过和撤销项；开放文本中的完成度另行判断 | 后续评价或已有结构化记录，不为首版新增模型工作 |
| 交接覆盖 H | 结构层为必需字段及引用存在项 / 当前适用项，另列未知与不适用；语义层单列核验 | 后续交接功能。结构完整不证明接手成功 |
| 交接损失 L | 以预先列出的关键项和接手结果核对遗漏、误记、未能定位的项数 | 后续实验结果，不是首版实时指标 |

P 的前提是字段语义、窗口口径、模型和主会话来源已核实。同版本 [TokenUsage::non_cached_input](https://github.com/openai/codex/blob/rust-v0.166.0-alpha.5.1/codex-rs/protocol/src/protocol.rs#L2660)从 input_tokens 中减去 cached_input_tokens，支持 input_tokens 已包含这部分缓存输入的判断。I 使用完整 input_tokens，不减去或重复加入缓存读量；cache_write_input_tokens 也不能未经 provider 语义核验就额外加到 P。对 session/thread、agent_id/agent_type 的映射须用目标入口验证后排除子代理和其他会话，不能只凭标记缺失就断定是主会话；归属不明则 P 未知。最近请求输入不等于此刻完整上下文，W 缺失或模型切换后等待有效新测量。

W 指与该请求的模型和运行时一致、已验证能作为输入占比口径的窗口值。探针需要说明它与模型标称最大窗口、运行时预留和压缩触发配置的关系，不能把这些值当成同一个量。若无法确认，W、P、B 均保持 unknown。

数据缺失时返回 unknown。[官方 Hooks 文档](https://learn.chatgpt.com/docs/hooks)说明 PostModelRequest 报告每次请求尝试的结果，用量在可获取时提供，否则为 null；不能假设失败、取消或成功请求都有用量。一个用户回合内可能有多次请求，测量不限于回合结束。

每个快照保留测量时点。只有程序实际观察到后续的新用户回合、模型切换、压缩，或已接入的输出/工具事件而没有有效新测量时，才标为过时/等待新样本；不能靠模型猜测是否有变化。对无法完整观察的间隔标明“采样时数据，当前覆盖未知”，不因未收到事件就断言没有变化。S1/S2 不预测缺值，也不把最近请求输入称为实时上下文占用。

后续若评价 V，只使用有效约束：用户明确修改或废止的要求不算遗忘；没有执行证据的模型自述不算核验通过。网络、权限、工具故障即使多次发生，也不能据此推出换 session 有用。

## 从指标到行动

四档都输出建议分和三种状态：`scored`（有足够数据）、`insufficient_data`（待评估）和 `disabled`（档位未启用）。分数后给出测量原因、覆盖范围和可选行动；有分不等于保证继续成功，关注压力也不等于必须换会话。

S1/S2 的零模型流程为：接收事件 → 核验版本、来源和新鲜度 → 更新 N、I/W/P、C 及已启用的确定性辅助项 → 按档位固定规则生成建议分 → 去重后显示原因与选项。S3/S4 在同一流程中增加已获准的语义证据，再由程序生成同一格式的分数；整个流程都不自动切换 session。

| 条件 | 状态与显示 | 可选行动 |
| --- | --- | --- |
| I、W 不能可靠对应，测量过时，或所需事件缺失 | `insufficient_data`，score 留空，写明缺失或过时原因；可同时展示已核实的回合数/事件 | 继续原任务或自行整理；不补推压力值 |
| 有效证据达到当前档位的最低要求，未达到候选区间 | `scored`，显示建议分、数据时点和覆盖率 | 用户可以继续，不暗示已检查所有语义质量 |
| 有效证据达到当前档位的最低要求，达到已配置的候选区间 | `scored`，显示建议分、来源时点及“未校准规则” | “可自行整理检查点，或自行准备交接后，在安全边界自行开新 session” |
| 已观测 PreCompact/PostCompact 等候选事件 | 记录事件，压力转为等待新样本；次数按已验证口径，否则未知 | 记录边界，等有效新测量；不因收到事件就宣称压缩成功或风险清零 |
| 只有轮数多，或已接入的辅助源只报告网络、权限、工具失败 | 显示背景数量或可核实的故障；未接入辅助项就标未知，不要求接入后才能运行核心规则 | 按问题原因处理，不单独提高建议分，也不做语义归因 |
| 某数据源提供明确的 ContextWindowExceeded 错误类型 | 显示容量错误及请求状态，不称为智力或质量诊断 | 提醒核对上下文、整理或考虑交接；若只有未经核实的错误文本，仅展示故障，不猜错误类型 |

候选区间以配置值 T 表示，例如 P 达到 T 时触发；本报告不给未经验证的默认数值。实现时须在验证字段口径后明确设置并展示其未校准状态；尚未配置时只展示测量和“提醒区间未配置”，不能假装规则已判断正常。用户接受粗略提醒，不等于接受任何隐藏阈值或已验证效果。

这些规则允许在尚无语义质量证据时给出粗略的“考虑交接”选项，不要求先让模型核对遗忘或交接内容。只有在后续实验充分支持时，才可以把某套分数称为经过校准的切换建议或概率。

假设例子，均为规则说明，不是实测或默认阈值：

| 情况 | 程序读取的观测 | 示例输出与边界 |
| --- | --- | --- |
| 35 轮，但最近输入占比低 | N=35；P 有效且未达到所配置的候选区间 | `S1 / 24分 / scored`；可以继续，不因轮数多而要求换会话，也不声称已核验质量 |
| 7 轮，但单轮内容很多 | N=7；P=82%；假设已达到用户可见的候选区间 | `S2 / 68分 / scored`；可考虑整理或交接；82% 和 68 分只是示例，不是已证明的临界值或概率 |
| 回合数已知，窗口未知 | N=12；I 可读但 W 未核实 | `S2 / 未评分 / insufficient_data`；显示回合数，压力待评估，不让模型猜窗口 |
| 收到压缩后事件，token 尚未更新 | 已记录 PostCompact，但没有有效新测量；完成次数按核验状态展示 | 保留此前分数和提醒历史，当前状态为待新样本；不沿用压缩前占比 |
| 输入占比低，却已经忘记要求 | P 有效且未触发；没有结构化违约证据 | `S2 / scored`，coverage 标明“连续性违约未评估”；这可能漏报，是零模型档位的已知局限，不能虚构一个“遗忘分”补齐 |

## 提醒规则

状态由档位规则生成，不合成为不可解释的质量总分。建议分是共同输出字段，不是已校准的质量概率。每个有效读数保留来源、版本范围、测量时点和覆盖信息；规则依据与测量置信分别记录，不能把“读数可信”说成“建议有效”。

S1 交付最简评分和提醒；S2 在 S1 基础上增加确定性覆盖并作为默认档位；S3、S4 只有用户选择并满足材料与预算边界时才增加模型分析。实验校准用于以后提高分数解释力，不是任何档位上线的前提。

提醒保护：

- 同一状态及原因持续时不重复打扰；压缩后的待测不算改善，不能据此反复重发压力警告。新有效样本显示改善后再恶化，才重新提醒；
- 压缩和模型切换后等待有效新样本；未知或采集失败不清除既有提醒记录，也不显示健康；
- 提供暂停或一次性忽略，由用户选择，记录该选择而不要求说明理由；
- 以 Hook/结构化事件为优先采集路径；S1/S2 不要求模型复述、解释或在回复末尾附带分析，S3/S4 的模型输出也不能绕过共同输出结构；
- 采集或显示失败时让原任务继续，在独立监控状态中记录错误，不能把失败当零值；
- 阈值配置带 value、status、source、calibrated_on、model_scope 和 runtime_scope；未配置和未校准分别展示，不套用社区项目常量；
- 没有可靠 W 时 P、B 固定为 unknown，不用轮数、字符数或模型猜测替代；
- 后续实际交接由用户发起。提示本身不执行保存、撤销、重试或外部操作，存在运行中写入或不确定结果时不能把换会话当作恢复手段；分数不自动升级档位。

## 交接格式和接手流程

本节保留为后续可选能力，不进入 S1/S2 的实时监控或提醒前提。首版可以建议考虑交接，但不自动生成交接文案，不调用模型补齐内容，也不要求当前任务代理额外总结。

未来由用户选择交接时，handoff 文件放在项目内 .handoff/，使用固定字段：

goal、authorized_actions、constraints、decisions、rejected_options、changed_files、verified、unverified、tests_and_results、open_questions、next_steps、evidence、generated_at、source_turn_ids。

只在用户选择交接时生成文件。已有结构化记录可直接填入，其他内容由用户补充，或另行选择有明确模型预算的生成方式；固定模板不等于能零模型生成完整语义交接。排除凭据、访问令牌和不必要的个人信息，优先记录事实、文件引用及来源位置。少量授权原话如确有必要，须在当前允许的本地范围内引用；不强制把授权改写成可能变义的句子。authorized_actions 记录已有允许范围，handoff 不能扩大它。安装时须说明 .handoff/ 默认不进入 Git；保存份数、期限及按文件删除方式写入配置，由用户选择，不能静默清理原始证据。

新 session 接手时：

1. 读取 handoff；
2. 检查 workspace、Git 状态和分支；
3. 只重跑 handoff 标为需要重跑的验证；
4. 用不超过五行复述目标、约束、已完成内容和下一步；
5. 在已有明确授权内继续；只有新的、未被授权的外部动作才请求确认。交接不能自动扩大授权，也不能让已有授权无故失效。

交接功能的初版由用户主动选择文件，核对任务标识、版本和时效性后载入。以后若支持 SessionStart，仍需明确匹配当前任务，不能盲目载入目录中最新文件。接手代理读取和核对交接会产生模型工作，费用须计入切换策略，不计作零模型监控的既有能力。

## 分阶段实施

四个档位按 S1→S4 逐步交付，每档完成后都能独立运行、交互和验收；完成后仍可作为日常档位保留。默认使用 S2。当前不启用根据分数自动升级档位，用户明确选择 S3/S4 后才增加模型工作。

### S1：最简评分版，监控额外模型调用 0

可用结果：读取已验证范围内的 N、I/W/P、C，执行最简确定性规则，返回共同输出结构中的建议分、原因、覆盖率和可选行动。S1 的分数由版本化的确定性映射 `f_S1(N, I, W, C, config)` 计算并限制在 0–100；`config` 必须公开记录信号、权重或分段、候选区间和未校准状态，不能把参数藏在代码里。W、I 或必要事件不足时，S1 返回 `insufficient_data` 和已核实读数，不把未知当作低分。S1 是可单独启用的最小闭环：它既能读数，也能评分并通过选定出口交互；它不是只显示原始读数。

先经单独授权做能力探针，核验 UserPromptSubmit、模型请求事件、压缩事件及数据时序。确定人类回合与 native turn 的映射；对中途补充消息、取消、重试和分叉分别核对，不能直接用 turns 数组长度代替人类回合数。历史总数只有在获准读取历史、核验分页和继承关系后才能标注；否则显示接管后的覆盖数，模型不补猜历史。

候选实现只需采集/解析、共享状态、最简规则和共同显示结构；不预建语义分类器、handoff 生成器或模型评审服务。状态按 thread、模型、运行时版本和压缩时期区分，使用原子写入、锁和事件去重；沿用已有跨账户共享位置的独立命名空间。内部子代理不进入人类回合数。

验收：字段存在、实际投递、口径正确和显示可见分别记录；读数带范围与时点；缺失项为未知；给定事件回放能复现计数、去重和分数；S1 的初始显示出口明确选为 Stop Hook 的 `systemMessage`，并通过 live probe 核验投递和界面可见性；不能用模型复述来补显示；监控额外模型调用为 0；主任务正常继续。若该出口不可见，S1 的显示验收不通过，不自动改用标题或模型输出。

### S2：默认零模型增强版，监控额外模型调用仍为 0

可用结果：在共同基础读数上增加已经验证的近期变化、确定性辅助事件、压缩边界处理和去重保护，生成更充分但仍未校准的建议分。S2 是默认档位，兼顾低成本、可解释性和比 S1 更完整的确定性证据。

候选显示出口为 Stop 的 systemMessage：状态或原因实质变化时才发送，不返回 decision:block、continue:false 或 additionalContext，不将提示注入模型评估；PostModelRequest 只采集。[官方 Hooks 文档的 Common output fields 表](https://learn.chatgpt.com/docs/hooks#common-output-fields)列出 Stop 支持 systemMessage，并将其效果描述为 UI/事件流警告；这是设计依据，目标桌面的可见性和实际路由仍须实测。若不可见或只能由模型处理提醒，S2 显示验收不通过；需要另行确认替代显示方案，不能悄悄让主代理复述，也不做 DOM 注入。

标题前缀保留为后续集成选项，不能在候选显示失败时自动启用。需先确认格式和升级范围，通过正常安装器更新包与回执，验证手动保护、原三段内容和跨账户状态。前缀只能由程序从监控结果拼接，不交给模型解释、生成或决定；还须验证新增状态不会经标题回读等路径进入模型请求。未证明这条边界前，标题路径不能用于通过 S2 验收。既有标题语义维护继续原流程，监控不读取其含义作为健康信号。

验收：给定相同事件和规则配置能产生相同状态、建议分和原因；未配置、缺失和过时不显示为健康；同状态不反复打扰；提醒在目标桌面可见；systemMessage 或其他显示结果不进入后续模型请求输入、不改变后续测量，须由 live probe 验证；不阻断回合、不自动切换、不覆盖手动标题，切换账户后状态能延续；监控额外模型调用仍为 0，包含附加评估指令在内的模型工作为 0。S2 的显示验收在 probe 通过前保持未验证。

### S3：最小必要语义版

可用结果：独立读取共同基础读数，并增加一项或一组最必要的开放语义检查，例如只检查结构化关键约束是否可能被遗漏，或解释一个确定性规则无法归因的重复失败。S3 只读取完成该检查所需的最小材料，目标是减少影响最大的漏报，属于待验证目标，不承诺更准；它不要求先运行 S2。

候选模型路径是独立的有界评估请求；也可以在得到单独授权后，把有限材料经 additionalContext 交给主模型，但这种路径会改变主会话输入并增加耦合。两种路径不能混称为“Hook 自己分析”。模型返回标签、证据片段或未知，程序再按共同规则生成建议分；模型不直接决定最终分数。

验收：明确材料白名单、输入上限、触发频率、请求和重试上限；S3 失败、标签缺失、模型返回“未知”或材料不足时将 `score_status` 置为 `insufficient_data`，不回落到 S2 分数，也不计为 0；模型调用和输入量可审计；同一结构输出仍可与 S1/S2 结果比较；抽样人工核验模型标签；用户明确选择后才启用，不自动升级、不自动切换。

### S4：扩大证据的语义版

可用结果：独立读取共同基础读数和 S4 获准的相关证据，例如选定的任务摘要、已确认决定、验证结果和近期轨迹，做交叉核验后输出同一建议分结构。S4 的目标是提高覆盖范围，而不是把“材料更多”当作准确率证明；它不要求先运行 S3。

验收：明确新增材料范围、隐私和留存边界、输入 token 上限、触发频率、总请求上限和实测开销；记录哪些证据被读取、哪些仍未知；模型标签经过人工或独立规则抽样核验；S4 失败、标签缺失、模型返回“未知”或材料不足时将 `score_status` 置为 `insufficient_data`，不回落到 S2/S3 分数，也不计为 0；S4 分数可以高于或低于其他档位；用户明确选择后才启用；任何失败都不降级成“低风险”。

### 后续验证与逐步升级

先验证 S1、S2 的采集、算术、规则和显示，再分别验证 S3、S4 的模型调用、材料边界和标签稳定性。比较各档位时使用共同的任务、切换目标和输出结构，分别报告未知率、误报/漏报、提前量、用户打扰、模型调用、输入量、等待时间和费用。只有重要漏报在 S2 中反复出现，并且 S3/S4 有可验证的收益预期时，才扩大模型材料或请求上限。

交接生成、语义分析、继续/压缩/新 session 三臂实验均为后续能力，不是 S1/S2 的依赖。token 解析、规则、交接和实验逻辑不进入 title_guard.py，不以扩大标题模型职责来规避 S1/S2 的零模型边界。

## 后续验证

### 先验证采集与提醒，再验证质量与切换收益

S1/S2 先做无需监控模型参与的事件回放、算术核对和显示验收；S3/S4 再增加模型调用、材料范围和标签稳定性检查。以重复、缺失、乱序、取消、压缩前后、模型切换、重连和跨账户续聊等案例检查状态；这些检查验证实现正确，不验证规则或模型能否识别质量下降。实测 Hook、独立评估请求和常驻路径的开销分别报告；未选用的路径不预先引入。

评价提醒时分别报告：未知率、每百个已覆盖人类回合的提示数、误报/漏报、提前量和用户打扰。精确率、召回率须明确标签定义、判定者与统计单位；没有独立质量标签就只能报告使用体验，不能把用户采纳提示当作“该换会话”的真值。人工抽样和已有验收结果可用于检查，开发期模型标注不是默认前提。

若后续评价语义质量，先定义连续性违约：

- 已确认约束被遗漏；
- 已确认决定被推翻且没有新确认；
- 已完成文件、测试或错误状态被丢失；
- 同一失败路径连续重复；
- 已完成工作被重新探索；
- handoff 与 workspace 状态不一致。

由不看规则输出的独立判定者标注轨迹。模型若参与标注，需说明输入、调用数和人工核验，不能把它当唯一真值。记录用户明确更改的要求，排除“任务本来就变了”的情况。

决策实验固定同一任务起点、模型、版本、commit 和工具权限，比较：

1. 继续原 session；
2. 先压缩再继续；
3. 新 session 加结构化 handoff。

在预先登记的同一切换点，从相同代码、外部工具及任务状态分出三臂；第三臂用 thread/start 新建干净线程，仅加载冻结的 handoff。其他臂保留各自对应的上下文。handoff 的生成者、模板、可读材料与生成开销事先固定，所有自动压缩单独记录。fork 若保留历史，只能用来保存或重放旧上下文，不算干净线程。

三臂能估计“新会话加交接”这个完整策略的实际价值，不能把收益归因于重置本身。第三臂失去历史上下文也是策略的一部分。若需要分解原因，增加“新会话只给当前完整 brief”的第四臂：它只回答没有 handoff 时重置的表现，不同时修改 handoff 模板。不同模板属于另一个可选实验。结论只适用于冻结的交接生成器、模板、切换点和模型版本。

策略比较的切换点按预先固定的任务里程碑或回合位置确定，不能事后由待评估检测器选择。验证完整监控策略时另做“检测器选点+行动”的实验，避免把这两个问题混合。自动压缩作为各臂的实际行为保留，并按发生/未发生分层报告。

主要结果：

- 需求覆盖和任务完成；
- 测试通过率和新增回归；
- 返工次数、重复工具调用和重复文件探索；
- handoff 遗漏；
- 总 token、缓存 token、等待时间和费用。

主要质量终点定为：在约定总预算内，任务所有必需验收项通过，且无关键约束违约的任务比例。需求部分完成度、返工、交接损失为次级指标，成本与耗时排在其后；原始失败和超时计入分母。实验登记必须固定可接受的质量损失界限 δ。本方案提出 δ=0 作为质量优先的保守候选要求，不把它说成论文证明的数值；用户若接受小幅质量取舍，须在实验前明确更改。小样本无法排除损失时只报告探索结果，不能把策略升级为经过校准的有效切换建议。

质量优先比较 C（新会话+交接）对 A（继续），再报告 B（压缩）的差异及多重比较处理；不能事后挑选最有利的终点。每个任务配对、重复运行，随机执行顺序；任务族、模型、推理档位、权限和代码起点固定。报告任务级差值及不确定区间，不能把同一任务中的模型请求当独立样本。样本量由先导方差、最小有意义改善和预算决定，本阶段不给固定次数。

实验前登记失败/超时是否计入、评分规则、最大运行次数和费用上限，保留未参与调参的任务族。若违反关键约束、交接造成外部效果不确定或环境不可复现，暂停受影响条件；不能删掉失败运行来改善结果。质量差于继续条件、或证据不足以排除有意义损失时，不将策略标为经过校准的切换建议；任何版本都不自动替用户切换。检测误报/漏报、策略净收益与用户打扰频率分别报告。

实验使用自建或公开合成任务，脱敏后只保存必要事件和结果。用户真实历史会话需要另行授权。成本按成功和失败任务一并报告，计入交接生成、读取、重建、缓存变化、监控及可选评估开销；不把节省 token 自动算成节省费用。任务代理正常执行的模型费用与监控额外费用分别记账，再计算整项策略的净收益。
